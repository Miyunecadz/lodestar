`test-engine.sh` verifies the engine against hand-written copies of five rules; `validate.py` checks only that a catalog pattern compiles. Nothing asserted that a shipped rule, installed as-is, produces the verdict its title promises — so twenty-one guardrail patterns, described in `docs/CONCEPTS.md` §4 as the product, had no behavioural coverage at all. Closes #26.

The gap is silent by construction. A tightened regex that accidentally stops matching is indistinguishable from a working one, and the failure mode is non-enforcement. It is also the gap that let #24 and #29 exist.

### Added
- **`test-catalog.py`** (new CI gate, 84 cases across all 21 guardrails) — installs the **real** `kit/catalog/guardrails/<id>.md` into a throwaway workspace, applying the same `id:` → `name:` transform `/lodestar-guardrails` §5 does, and asserts the engine's verdict. Hand-written copies in a test file cannot do this: when the copy and the catalog drift apart, both keep passing. The install transform itself was previously assumed rather than exercised.
- **`.github/fixtures/guardrails.tsv`** — `rule-id | verdict | input | context`, with context for the default branch, untracked files, and `match: content` rules. Cases pin claims the rule bodies already make: the `.env.local.example` lookahead, `allow_paths` exempting temp deletes, `match: argv` ignoring quoted text, each migration rule staying inside its own stack.
- **`validate.py` requires a positive *and* a negative fixture per guardrail.** Both directions: a rule with only positives cannot regress into matching everything, and a rule with only negatives cannot regress into matching nothing.

### Notes
- **The harness was mutation-tested, and the first version was wrong.** Breaking a pattern and dropping a copied field were both caught; widening a migration rule to `stacks: [all]` was **not** — its wrong-stack negative was passing on untracked-ness rather than on scope, so it asserted nothing. Every file fixture is now committed unless its row says `untracked=1`, and all three migration rules now fail that mutation. `allow_if_untracked` gained its own explicit cases in the process.
- **Three entries are `emits: settings-hook`** (`autolint-on-edit`, `php-autolint-on-edit`, `python-autolint-on-edit`). Those never reach the engine — the picker writes a `settings.json` PostToolUse hook whose matcher uses the pattern — so their fixtures assert the pattern directly. Running them through the engine would test a path that does not exist in production.
